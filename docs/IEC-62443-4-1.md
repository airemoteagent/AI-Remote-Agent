# IEC 62443-4-1 — Secure Product Development Lifecycle (SDLC) Mapping

> **Status:** evidence-based alignment · **Applies to:** remote-agent (device daemon / IACS component)
> **Standard:** IEC 62443-4-1:2018 — Security for industrial automation and control systems —
> Part 4-1: Secure product development lifecycle requirements.
>
> This document maps the **13 process requirements (SM-1…SM-13)** of IEC 62443-4-1
> to the concrete process, artefacts and tests in this repository. It is the
> evidence base a certification body reviews; it is **not** a certificate.
> Formal IEC 62443-4-1 certification requires an independent assessment — the
> gap between "evidence in the repo" and "certified" is stated explicitly at the end.

---

## 0. Scope and product definition

**Product under assessment:** the remote-agent **device daemon** — a headless,
egress-only Node.js process (macOS / Linux / Windows / WSL2 / Raspberry Pi) that
polls a control plane for work, executes local tools behind a policy gate, and
streams results back. It is treated as an **IACS component (62443-4-2)** when
deployed on operator consoles, edge gateways or lab instruments.

**Security lifecycle owner:** Product Security & Compliance (see
`docs/COMPLIANCE-ROADMAP.md`).

**Out of scope (stated plainly):** the remoteagent.online cloud SaaS is a
separate product; hardware-backed key storage, hosted SSO/SCIM and an
independent audit remain operational work.

## 2. Detail per process requirement

### SM-1 — Security management
A security policy, roles and a documented process exist and are treated as
product requirements, not afterthoughts.
- **Policy & decision rules:** `docs/COMPLIANCE-ROADMAP.md` §6 (non-negotiables).
- **Threat model as living artefact:** `docs/additional-documents/THREAT-MODEL.md` (STRIDE).
- **Reporting channel:** `SECURITY.md` + `docs/.well-known/security.txt`.
- **Traceability:** every headline security claim maps to a test file (§G5).

### SM-2 — Security requirements specification
Security requirements are derived from the threat model and specified before
implementation.
- **Sources:** STRIDE analysis (8 abuse scenarios) → mitigations → policy rules.
- **Specified controls:** local policy authority, argv shell, workspace files,
  SSRF-safe network, prompt-injection trust boundaries, hash-chained audit.
- **Machine-checkable form:** `docs/POLICY.md` (v1 tier map + v2 rule grammar).
- **Matrix:** `docs/SECURITY-REQUIREMENTS-TRACEABILITY.md` links each requirement
  to design modules and tests.

### SM-3 — Secure by design
The architecture removes whole classes of risk rather than patching them.
- **No inbound ports** — the daemon polls HTTPS; nothing can reach the device.
- **Egress-only** — device-initiated connections only.
- **Local policy authoritative** — a malicious control plane can request, never widen.
- **No secrets on device** — provider keys never leave the cloud; child envs scrubbed.
- **Structural injection resistance** — argv execution, per-segment allowlists,
  `O_NOFOLLOW`+fstat, DNS-pinned SSRF checks.

### SM-4 — Secure implementation
Coding rules enforce the design at the implementation level.
- **Never a shell string** — `shell.js` parses to argv, `spawn(shell:false)`.
- **Path safety** — realpath containment + `O_NOFOLLOW` + fstat (TOCTOU).
- **Crypto hygiene** — CSPRNG token generation; Ed25519 via `node:crypto`; no
  custom cipher implementation.
- **Redaction** — secrets excluded from logs and child environments.
- **CI guard:** a CI assertion fails if `shell.js` ever passes a raw string to
  PowerShell (`ci.yml` Windows smoke step).

### SM-5 — Security verification & validation testing
Security properties are verified automatically on every change.
- **Red-team suite:** `apps/desktop/test/security.test.mjs`, `prompt-injection.test.mjs`,
  `system-cmd.test.mjs`, `update-integrity.test.mjs`.
- **Coverage breadth:** command injection, path traversal, symlink escape, TOCTOU,
  SSRF/rebinding, redirect-to-metadata, prompt injection, audit tampering.
- **CI:** Node 20/22/24 × ubuntu/macos/windows + CodeQL + gitleaks + `npm audit`.
- **Baseline:** 451 tests, 0 failures (~29 s).

### SM-6 — Management of security-related issues
A defined process handles reported security issues end-to-end.
- **Intake:** `SECURITY.md` disclosure + `security.txt` + `security-review.yml` template.
- **Targets:** acknowledge ≤ 48 h (or 5 working days for CRA channel), triage
  ≤ 15 days, high-severity fix ≤ 90 days, coordinated public disclosure.
- **See:** `docs/VULNERABILITY-MANAGEMENT.md` for the full process and SLAs.

### SM-7 — Security update management
Updates are integrity-verified, staged and rollback-capable.
- **Client self-update:** `update.js` verifies SHA-256 and extracted-version match,
  with rollback on failure (`~/.remote-agent/update.json` lifecycle record).
- **Installer:** `install.sh`/`install.ps1` enforce checksums; `REMOTE_REQUIRE_CHECKSUM=1` hard-fails.
- **Release pipeline:** `release.yml` builds source archive + `SHA256SUMS` + SBOM
  + provenance attestation; tag must equal package version.
- **Fleet staging:** `packages/engine/src/upgrade.js` (canary, health-gated rollout).

### SM-8 — Security guidelines
Operators receive explicit hardening and deployment guidance.
- `docs/POLICY.md` (presets + rule grammar), `docs/SECURITY-AUDIT.md` (adopter checklist),
  `docs/DEPLOYMENT-GUIDE.md` (launchd/systemd/proxy), `docs/WINDOWS.md`,
  `docs/RUNBOOKS.md` (disk/service/certificate/network).

### SM-9 — Security requirements for third-party components
The supply chain is minimized and verifiable.
- **One runtime dependency** (`ws@^8.18.0`); everything else devDependency or
  optional peer loaded dynamically (OTel).
- **SBOM:** `sbom.cyclonedx.json` (CycloneDX 1.5).
- **Dependency audit:** `npm audit --audit-level=high` and `npm audit --omit=dev` in CI.
- **Plugin trust:** signed plugin manifests (`plugin-manifest.js`, Ed25519) + signed
  marketplace index (`marketplace-index.js`) — third-party tools denied by default.

### SM-10 — Security review
Independent review gates are defined and evidenced.
- `docs/SECURITY-REVIEW-SCOPE.md` and `docs/additional-documents/SECURITY-AUDIT.md`
  define what is reviewed and how to verify it.
- **CodeQL security-extended** runs in CI with SARIF upload.
- **Secret scan (gitleaks)** runs on every CI pass.

### SM-11 — Security problem resolution
Resolved issues are fixed with regression coverage and public advisory.
- Each fix lands with a regression test in the relevant suite.
- Advisories follow the coordinated-disclosure policy in `SECURITY.md`.
- `npm audit` fail-gate blocks known-vulnerable dependency states.

### SM-12 — Security-relevant product documentation
Documentation is complete, versioned and shipped.
- **Public API contract:** `types/index.d.ts` + `docs/STABILITY.md`.
- **Tool reference:** `docs/TOOLS.md`; **policy reference:** `docs/POLICY.md`.
- **Compliance index:** `docs/COMPLIANCE-MATRIX.md` ties every framework to evidence.

### SM-13 — Security testing
A dedicated, adversarial test discipline exists beyond functional tests.
- `apps/desktop/test/security.test.mjs` (red-team), `prompt-injection.test.mjs`,
  `system-cmd.test.mjs`, `files`/`net`/`shell` adversarial cases.
- **Reproducibility gate** and **secret scan** in `ci.yml`.
- **Lifecycle acceptance** dry-runs the installers and the package state machine.

## 3. What is NOT claimed

- **No independent IEC 62443 certification.** This document is the evidence base
  for a future assessment; certification requires an accredited body.
- **No hardware-backed key storage** (the device token lives in a 0600 file).
- **No hosted SSO/SAML/OIDC or SCIM** (enterprise identity is roadmap work).
- **No formal security-level (SL) claim** until a component assessment maps CRs to
  SL targets — see `docs/IEC-62443-4-2.md`.
